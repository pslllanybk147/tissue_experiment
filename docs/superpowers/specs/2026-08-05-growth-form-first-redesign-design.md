## 1 · ปัญหาที่แก้

### 1.1 อาการที่พบ

ระบบปัจจุบันมีโครงเนื้อหาและระบบหลักฐานที่แข็งแรง แต่ **ประตูทางเข้าปิดตายสำหรับมือใหม่**

| อาการ | หลักฐานในระบบปัจจุบัน |
|---|---|
| หน้าแรกถามคำถามที่มือใหม่ตอบไม่ได้ | `plant-picker.tsx` ขึ้น "จะเพาะต้นอะไรดี" แล้วแสดงชื่อวิทยาศาสตร์ |
| ไม่มีคลังคำศัพท์ | ขั้น `select-explant` ใช้คำว่า "ข้อ" และ "ตาข้าง" โดยไม่มีที่ไหนอธิบาย |
| ภาพไม่ช่วยตัดสินใจ | `illustrations.tsx` เป็น SVG วาดเอง · `referenceImages` เป็นลิงก์ภายนอกที่ไม่ได้ระบุตำแหน่งตัด · `project_summary.md §12` ยอมรับเองว่ายังไม่มีภาพตรงพันธุ์ |
| ครอบคลุมแคบ | มีคู่มือ 3 ชุด ทั้งหมดอยู่ในสกุล Philodendron |
| ไม่มีทางเข้าจาก "ปัญหา" | `troubleshooting.ts` มีคลังอาการกลาง แต่เข้าถึงได้ผ่านขั้นตอนเท่านั้น |
| ไม่มีทางเข้าจาก "ยังไม่มีต้น" | ไม่มีหน้าที่ตอบว่ามือใหม่ควรเริ่มจากพืชแบบไหน |

### 1.2 painpoint ของวงการที่ยืนยันแล้ว

จากการค้นเอกสารและแหล่งของวงการ ปัญหาที่พบซ้ำมากที่สุดคือ

1. **การปนเปื้อน** — โดยเฉพาะ endophyte ที่อยู่ในเนื้อเยื่อ ฟอกผิวไม่ตาย แสดงอาการหลัง 2–4 สัปดาห์
2. **การเกิดสีน้ำตาล/ดำจากฟีนอลิก** — PPO ทำปฏิกิริยาตอนตัด ได้ quinone ที่ฆ่าชิ้นพืชเอง
3. **ตำแหน่ง explant ต่างกันรายชนิด** — ยอด ข้อ ราก ใบ หรือ callus
4. **ความไวต่อสารฟอกต่างกัน** — ช่วงระหว่างฆ่าเชื้อไม่หมดกับฆ่าชิ้นพืชแคบมาก
5. **Vitrification และ recalcitrance**
6. **การตายตอนออกขวด**
7. **feedback loop ยาว** — ทำผิดวันนี้ รู้ผลอีกสามสัปดาห์ จับคู่สาเหตุกับผลไม่ได้

ข้อ 3 และ 4 ตรงกับที่เจ้าของระบบประสบเอง ข้อ 7 คือช่องว่างที่ระบบนี้แก้ได้
เพราะมีโครงบันทึกรอบเพาะรายขั้นอยู่แล้ว

### 1.3 สาเหตุราก

ระบบเดิมใช้ **สายพันธุ์เป็นแกนเดียว** จึงเกิดผลสองอย่างพร้อมกัน

- ผู้ใช้ต้องรู้ชื่อสายพันธุ์ก่อนถึงจะเข้าระบบได้ ซึ่งมือใหม่ไม่รู้
- เนื้อหาทุกชิ้นผูกกับสายพันธุ์ ทำให้ต้องเขียนคู่มือใหม่ทั้งเล่มทุกครั้งที่เพิ่มพืช

## 2 · แนวทางที่เลือก

**ทำ "ทรงการเติบโต" (growth form) ให้เป็นแกนของระบบ** โดยสายพันธุ์กลายเป็นชั้นล่างสุด

```
core-steps  (1 ชุด)        ขั้นตอนกลาง 14 ขั้น            มีอยู่แล้ว
  └ form    (~8)           ทรง · คำศัพท์ · จุดสังเกต       ใหม่
      └ genus (~30-40)     สารฟอก · สูตร · ตำแหน่ง        ใหม่
          └ species (น้อย) เฉพาะที่ต่างจริง               มีอยู่แล้ว 3 ไฟล์
```

เหตุผลที่ทรงเป็นแกนได้จริง คือ **สิ่งที่มือใหม่ต้องรู้เพื่อลงมือไม่ได้แปรตามสายพันธุ์
แต่แปรตามทรง** จุดสังเกตที่ต้องหาให้เจอมีไม่กี่จุด (ข้อ ปล้อง ตาข้าง ยอด ก้านใบ กาบใบ)
และจุดเหล่านี้หน้าตาเหมือนกันในพืชที่ทรงเดียวกัน

แนวทางที่พิจารณาแล้วไม่เลือก

- **คงแกนสายพันธุ์ แล้วเติมคลังคำศัพท์กับภาพ** — เร็วและเสี่ยงต่ำ แต่แก้แค่ปัญหาการอ่าน
  ไม่ได้แก้ปัญหาว่าต้องรู้ชื่อต้นก่อนถึงจะเข้าระบบได้ และภาพยังผูกกับสายพันธุ์แบบหนึ่งต่อหนึ่ง
- **ใช้อาการเป็นแกน (diagnostic-first)** — แก้ painpoint ข้อ 7 ตรงที่สุด แต่ใช้ไม่ได้กับ
  ผู้ใช้ที่ยังไม่เริ่มลงมือ จึงเหมาะเป็นหนึ่งในประตู ไม่ใช่แกน

## 3 · โครงเนื้อหา

### 3.1 ชั้นทรง · `src/lib/manual/forms/`

โฟลเดอร์ใหม่ขนานกับ `species/` **ไม่แก้ `core-steps.ts`**

```ts
/** จุดสังเกตบนต้นที่มือใหม่ต้องหาให้เจอ — คือ "คำศัพท์ที่ชี้ได้" */
export type Landmark = {
  id: string;
  term: string;                       // "ข้อ"
  aka?: string[];                     // ["node", "ปม", "ปุ่ม"] ใช้ให้ค้นเจอด้วยคำที่คนพูดจริง
  whatItIs: string;                   // ห้ามใช้ศัพท์เทคนิคอื่นซ้อนในคำอธิบาย
  howToFind: string;
  confusedWith?: string;
  point?: { x: number; y: number };   // 0–1 บนภาพอ้างอิง มีได้เมื่อมีภาพเท่านั้น
  evidence: EvidenceRef;
};

export type GrowthForm = {
  id: string;
  label: string;
  plainDescription: string;           // ให้คนที่ไม่รู้อะไรเลยจำแนกต้นตัวเองได้
  referenceImageId?: string;          // optional — ระบบต้องทำงานได้โดยยังไม่มีภาพ
  landmarks: Landmark[];
  defaultExplant: {
    landmarkId: string;
    offsetMm: number;
    direction: "above" | "below";
    sizeMm: [number, number];
    evidence: EvidenceRef;            // เป็นข้ออ้าง ต้องมีที่มา
  };
  beginnerDifficulty: 1 | 2 | 3;
  whyThisDifficulty: string;          // เหตุผลจริง ไม่ใช่ดาวลอย ๆ
};
```

**ทรงตั้งต้น 8 ทรง**

| # | ทรง | ยาก | ตัวอย่าง | explant หลัก |
|---|---|---|---|---|
| 1 | เถาเลื้อย ข้อเห็นชัด | 1 | Philodendron, Monstera, Epipremnum | ข้อ + ตาข้าง |
| 2 | กุหลาบซ้อน ข้อซ่อนใต้กาบ | 3 | Anthurium, Alocasia | ก้านใบ / เนื้อเยื่อเจริญที่โคน |
| 3 | ต้นเดี่ยวมีเหง้า | 2 | ขิง ข่า ขมิ้น กล้วย | ตาบนเหง้า |
| 4 | ใบหนาไร้ลำต้นชัด | 2 | Sansevieria | แผ่นใบ |
| 5 | ไม้ใบมีตาที่โคนใบ | 2 | Begonia | แผ่นใบ + เส้นใบ |
| 6 | กล้วยไม้มีลำลูกกล้วย | 3 | Dendrobium | ตาข้างลำลูกกล้วย / เมล็ด |
| 7 | ไม้พุ่มเนื้อแข็ง | 3 | ชวนชม กุหลาบ | ยอดอ่อน / ข้อ |
| 8 | ไผ่และหญ้ามีข้อ | 2 | ไผ่ | ข้อ + ตาข้าง |

### 3.2 ชั้นสกุล · `src/lib/manual/genera/`

ชั้นที่ทำงานหนักที่สุดในเชิงความครอบคลุม เพราะโปรโตคอลเกาะกลุ่มตามสกุลมากกว่าตามชนิด
หน่วยของการเขียนคือ **รายการส่วนต่างจากชั้นบน ไม่ใช่คู่มือทั้งเล่ม** ประมาณ 30–60 บรรทัดต่อไฟล์

```ts
export type GenusPack = {
  id: string;
  growthFormId: string;
  scientificName: string;
  commonNames: string[];
  deviations: Record<string, StepOverride>;
  mediaRecipes?: MediaRecipe[];
  sourceIds: string[];
};
```

### 3.3 ชั้นสายพันธุ์ · `src/lib/manual/species/`

ไฟล์เดิม 3 ไฟล์ เพิ่มฟิลด์ผูกขึ้นชั้นบน

```ts
growthFormId: string;
genusId?: string;
traitIds?: string[];              // อ้างทะเบียนใน src/lib/manual/traits.ts (ดู 4.2)
cutMarkers?: CutMarker[];
```

`CutMarker` คือหมุดบนภาพต้นจริงของชนิดนั้น แยกจาก `Landmark.point` ซึ่งอยู่บนภาพอ้างอิงของทรง

```ts
export type CutMarker = {
  imageId: string;
  landmarkId: string;              // ต้องมีอยู่ในทรงของชนิดนี้
  point: { x: number; y: number }; // 0–1 บนภาพนั้น
  label: string;
  evidence: EvidenceRef;
};
```

### 3.4 การประกอบ

`resolve.ts` ปัจจุบันทำ `core → override → pack` อยู่แล้ว งานคือ**ต่อ cascade ให้ยาวขึ้น**
เป็น `core → form → genus → species` ตรรกะการทับค่าเดิมใช้ซ้ำได้ทั้งหมด
ค่าที่ resolve ได้จะพก `evidence` ของชั้นที่ให้ค่านั้นติดมาด้วย เหมือนที่ override ทำอยู่

## 4 · ค่าเชิงปริมาณและระบบหลักฐาน

### 4.1 ค่าเป็นช่วง ไม่ใช่ตัวเลขเดี่ยว

ตัวแปรที่ขยับความเข้มข้นและเวลาฟอกได้แรงที่สุด **ส่วนใหญ่ไม่ใช่ชนิดพืช**
เรียงตามน้ำหนักคือ ที่มาของต้นแม่ (กลางแจ้ง/โรงเรือน/ในขวด) · ชนิดและอายุเนื้อเยื่อ ·
สัดส่วนเนื้อด่าง · ฤดูกาล · แล้วจึงเป็นชนิดพืชเอง

ผลคือ **PP ที่ปลูกในโรงเรือน ต่างจาก PP ที่ซื้อจากแผงกลางแจ้ง มากกว่าที่ PP ต่างจาก
White Knight ที่ปลูกข้างกันในโรงเรือนเดียวกัน** ระบบจึงต้องแสดงค่าเป็นช่วงพร้อมตัวขยับ

```ts
export type Dose = {
  form: string;                  // ชื่อและรูปแบบที่ใช้จริง เช่น "น้ำยาซักผ้าขาว NaOCl 6%"
  low: number;
  high: number;
  unit: MeasurementUnit;
  durationMin: [number, number];
  movesLowerWhen: string[];
  movesHigherWhen: string[];
  evidence: EvidenceRef;
};
```

หน้าจอแสดงว่า "ช่วง 0.8–2% นาน 10–20 นาที · ต้นของคุณมาจากโรงเรือนและมีด่างมาก
จึงเริ่มที่ปลายต่ำ" แทนที่จะแสดงตัวเลขเดี่ยวที่ทำท่าว่าแม่นกว่าความจริง

> ตัวเลขทุกตัวในเอกสารนี้เป็นตัวอย่างโครงสร้างเท่านั้น **ห้ามนำไปใช้เป็นเนื้อหาจริง**
> ค่าจริงต้องผ่านการค้นหลักฐานตาม `newplant_protocol.md` ตอนเขียนไฟล์สกุล

### 4.2 แกนลักษณะพันธุ์ (Trait) ที่ตัดข้ามสกุล

ความด่างไม่ใช่ลักษณะของสกุลใดสกุลหนึ่ง Monstera albo, Syngonium albo และ Philodendron ด่าง
เจอปัญหาเดียวกัน จึงไม่ควรเป็นชั้นใน cascade แต่เป็น modifier แยกแกน

```ts
export type Trait = {
  id: "variegated" | "outdoor-grown" | "high-phenolic" | "soft-tissue";
  label: string;
  adjustments: {
    target: string;                          // เช่น "sterilize.dose"
    direction: "lower" | "shorter" | "add";
    why: string;
    evidence: EvidenceRef;
  }[];
};
```

### 4.3 ฮอร์โมนต้องเข้มกว่าสารฟอก

การตอบสนองทางสัณฐานต่อ BA/NAA/IBA ต่างกันตามชนิดจริง และพันธุ์ด่างมีปัญหาเฉพาะ
คือ cytokinin สูงเกินไปทำให้ได้ยอดเขียวล้วนหรือขาวล้วน ลายด่างหาย ซึ่งทำลายเป้าหมาย
ของการเพาะพันธุ์ด่างทั้งหมด

กฎคือ **ถ้าไม่มีงานตรงพันธุ์ ห้ามยืมค่าฮอร์โมนของสกุลมาแล้วนำเสนอว่าใช้ได้เลย**
ต้องแสดงเป็นช่วง ติดระดับ `adapted` และบังคับให้ทดสอบก่อน (ดู 4.5)

### 4.4 ระดับหลักฐานเพิ่มหนึ่งประเภท

`EvidenceLevel` เดิมมัดสองคำถามไว้ด้วยกัน คือ "ตรงพันธุ์แค่ไหน" กับ "มีงานรองรับแค่ไหน"
เนื้อหาระดับทรงจึงตกร่อง ทางแก้คือแยก **นิยาม** ออกจาก **ข้ออ้าง**

| ประเภท | ตัวอย่าง | ระดับ | เข้ากฎจุดอ่อนที่สุด |
|---|---|---|---|
| นิยาม/กายวิภาค | "ข้อคือจุดที่มีตาข้างและมักมีรากอากาศ" | `botanical-fact` (ใหม่) ต้องมี `sourceIds` | **ไม่** |
| ข้ออ้างเชิงวิธีการ | "ตัดใต้ข้อ 10 มม." | `species-direct` / `adapted` / `unsupported` เดิม | **ใช่** |

เหตุผลที่ยกเว้นนิยามจากกฎจุดอ่อนที่สุด คือคำนิยามไม่ใช่คำแนะนำที่มีความเสี่ยง
และตรวจสอบได้จากตำราพฤกษศาสตร์เล่มใดก็ได้ ถ้านับเข้าไปด้วย ทุกคู่มือจะถูกลากลงเท่ากันหมด
ทำให้กฎเสียความหมาย ส่วน `defaultExplant` ยังเป็นข้ออ้างเต็มตัว ไม่มีการยกเว้น

### 4.5 ขั้นทดสอบช่วง

เมื่อค่าที่ resolve ได้ไม่ใช่ `species-direct` ระบบ **แทรกขั้นทดสอบช่วงเข้าไปในคู่มือ**
โดยให้ผู้ใช้แบ่งชิ้นพืชเป็นสามชุด ทดสอบปลายต่ำ กลาง และปลายสูงของช่วง แล้วบันทึกผล
ลงรอบเพาะ ชุดที่ไม่ติดเชื้อ**และ**ชิ้นไม่ดำคือค่าของต้นนั้น

นี่คือวิธีที่ห้องปฏิบัติการจริงใช้ และเปลี่ยน painpoint ข้อ 7 จากการลองผิดลองถูก
เป็นการทดลองที่ออกแบบไว้แล้ว โดยใช้โครง `/my/rounds` ที่มีอยู่เป็นที่บันทึก

### 4.6 ความครอบคลุมเป็นระดับ ไม่ใช่มีหรือไม่มี

| ผู้ใช้ค้น | ระบบให้ | ระดับ |
|---|---|---|
| Philodendron Pink Princess | คู่มือชนิด | ตรงพันธุ์ |
| Philodendron gloriosum | คู่มือสกุล Philodendron | ประยุกต์ |
| Scindapsus (ไม่มีในระบบ) | คู่มือทรงเถาเลื้อยข้อชัด | ประยุกต์ (อ่อนกว่า) |
| ระบุทรงไม่ได้ | บอกตรง ๆ ว่าระบุไม่ได้ แล้วขอรูป | — |

## 5 · เส้นทางและหน้าจอ

### 5.1 แผนผังเส้นทาง

```
/                      หน้าแรก 4 ประตู
/find                  ไล่ภาพหาทรง
/start                 ยังไม่มีต้น เรียงตามความยาก
/problem               เข้าจากอาการ
/form/<formId>         หน้าทรง
/guide/<slug>          คู่มือ (เดิม)
/guide/<slug>/step/<n> (เดิม)
/my/*                  (เดิม ไม่แตะรอบนี้)
```

คลังคำศัพท์ไม่มี route ของตัวเอง เพราะผู้ใช้ต้องการคำอธิบายตอนที่กำลังอ่านคำนั้นอยู่

### 5.2 หน้าแรก · สี่ประตูเท่ากัน

แสดงสี่ประตูขนาดเท่ากันในจอเดียว ไม่ชี้นำ เพราะสถานะตั้งต้นของมือใหม่กระจายครบทั้งสี่แบบ

1. **มีต้นอยู่ แต่ไม่รู้ชื่อ** → `/find`
2. **รู้ชื่อต้นแล้ว** → ค้นหา
3. **ยังไม่มีต้น** → `/start`
4. **ทำแล้วมีปัญหา** → `/problem`

ข้อบังคับร่วม คือไม่มีเมนูซับซ้อนบนหน้าแรก ไม่แสดงชื่อวิทยาศาสตร์ก่อนที่ผู้ใช้จะพร้อม
และทุกประตูต้องจบที่หน้าทรงได้เสมอ ไม่มีทางตัน

### 5.3 `/find` · ไล่ภาพหาทรง

คำถามภาพทีละข้อ 2–4 ข้อจบ **ปลายทางคือทรง ไม่ใช่สายพันธุ์** เมื่อได้ทรงแล้วใช้งานได้ทันที
ถ้าทรงนั้นมีคู่มือเจาะจงจึงค่อยเสนอเป็นตัวเลือกต่อโดยไม่บังคับ

ต้องมีทางออก "ไม่แน่ใจ" ที่ไม่ใช่ทางตัน และหน้าทรงต้องยอมรับได้ว่าผู้ใช้มาผิดทรง

### 5.4 กรณีค้นแล้วไม่เจอ

กรณีสำคัญที่สุดของประตูที่สอง ระบบเดิมมีคู่มือ 3 ชุด แปลว่าเกือบทุกคนจะไม่เจอต้นของตัวเอง
ระบบใหม่ต้องตอบว่ายังไม่มีคู่มือเฉพาะ แต่ต้นนี้อยู่ในทรงใด ใช้คู่มือระดับทรงได้
พร้อมระบุระดับหลักฐานและความเสี่ยงที่ต้องรู้

### 5.5 หน้าทรง `/form/<formId>`

เลย์เอาต์แบบ **การ์ดเรียงลงหนึ่งการ์ดต่อหนึ่ง landmark** โดยภาพเป็นช่องว่างที่เติมทีหลัง

เหตุผลที่เลือกแบบนี้แทนภาพเดียวมีหมุด คือมันทำงานได้ตั้งแต่วันที่ยังไม่มีภาพสักใบ
และโครงข้อมูลของมันเป็น superset — เมื่อมี `point{x,y}` แล้ว การ์ดชุดเดิมเรนเดอร์เป็น
หมุดบนภาพได้ทันที และเรียงต่อกันเป็นโหมดพาไล่ทีละจุดก็ได้ **ทั้งสามโหมดใช้ข้อมูลชุดเดียวกัน**

เมื่อยังไม่มีภาพ แสดงกล่องบอกตรง ๆ ว่ายังไม่มีภาพของทรงนี้ พร้อมทางเลือกให้ใช้รูปต้นของผู้ใช้เอง
**ห้ามใช้ SVG วาดเองมาแทนเพื่อให้ดูเหมือนมี**

### 5.6 ระบบคำศัพท์

ใช้ทะเบียนเดียวกับ `landmarks` ไม่แยกคลัง เนื้อหาห่อคำไว้ด้วย `<Term id="node">ข้อ</Term>`
แตะแล้วเด้ง sheet แสดง คืออะไร → หายังไง → อย่าสับสนกับ พร้อมภาพชี้จุดถ้ามี

เพิ่มเป็น **กฎเนื้อหาสำหรับมือใหม่ข้อ 3** ใน `project_summary.md` ว่าห้ามใช้ศัพท์เทคนิค
ที่ยังไม่มีในทะเบียน ถ้าจะใช้ต้องลงทะเบียนพร้อม `howToFind` ก่อน

### 5.7 `/problem` · เข้าจากอาการ

ใช้ `troubleshooting.ts` ที่มีอยู่ เข้าจากอาการที่มองเห็น ไม่ใช่จากขั้นตอน เช่น ขวดขุ่น ·
มีขนฟู · ชิ้นพืชดำ · อาหารเปลี่ยนสี · ไม่โตเลย · ต้นใสฉ่ำน้ำ · ตายตอนออกขวด
แล้วใช้ฟิลด์ `distinguish` ที่มีอยู่แล้วแยกอาการที่หน้าตาคล้ายแต่แก้คนละทาง

### 5.8 `/start` · ยังไม่มีต้น

เรียงทรงตาม `beginnerDifficulty` พร้อมแสดง `whyThisDifficulty` ที่บอกเหตุผลจริง

## 6 · ชั้นดีไซน์

ใช้ token ชุดเดียว สองสำเนียงตามโหมดการใช้งาน **ไม่ใช่สอง design system**

| โหมด | หน้า | ต้องการ | สำเนียง |
|---|---|---|---|
| อ่าน | หน้าแรก · `/find` · `/form` · `/guide` | สบายตา อ่านยาว ภาพเด่น | สมุดบันทึกพฤกษศาสตร์ — เส้นบาง เงานุ่ม พื้นอุ่น หัวข้อ serif |
| ลงมือ | `/my/rounds/…/step/<n>` | ตัวเลขชัด คอนทราสต์สูง อ่านตอนใส่ถุงมือ | เครื่องมือหน้างาน — ตัวเลขใหญ่ tabular พื้นเข้ม |

ต่างกันที่ค่าคอนทราสต์และขนาดตัวเลขเท่านั้น สอดคล้องกับ token ชุดนุ่มที่เริ่มไว้แล้ว
(`--pl-line-soft`, `--pl-shadow-soft`) ซึ่งเดิมวางแผนไว้เป็นเฟส 2 ของงาน nav/calculator

ภาษาเดิม Illustrated Step Book (เส้นขอบหนา เงาทึบ) ถูกแทนที่ เพราะแย่งความสนใจ
กับภาพต้นจริงที่ควรเป็นประธานของหน้า

โหมดมืดยังออกแบบที่ระดับ token ตั้งแต่ต้นตามหลักเดิม

## 7 · แผนเฟส

| เฟส | ทำอะไร | ผู้ใช้ได้อะไร | พึ่งภาพ |
|---|---|---|---|
| **0 · ฐานข้อมูล** | `forms/` · `genera/` · `traits` · ทะเบียนคำศัพท์ · ต่อ cascade · `botanical-fact` · `Dose` · เทสต์บังคับทั้งชุด | ยังไม่เห็นอะไร | ไม่ |
| **1 · ประตูและหน้าทรง** | `/` · `/find` · `/form/<id>` · term sheet · `/problem` · `/start` · retheme โซนอ่าน | ใช้งานได้จริงครั้งแรก | ไม่ |
| **2 · เนื้อหา** | เขียน 8 ทรง + ~10 สกุลแรก + ย้าย species เดิมมาผูก `growthFormId` | ครอบคลุมกว้างขึ้นมาก | ไม่ |
| **3 · ภาพ** | เครื่องมือปักหมุด รับทั้งรูปเจ้าของระบบและรูปผู้ใช้ + ภาพจริงทยอยลง | หน้าทรงยกระดับเป็นแบบมีหมุด | ใช่ |
| **4 · ปิดวง** | ขั้นทดสอบช่วงผูกกับ `/my/rounds` + retheme step runner | แก้ painpoint ข้อ 7 | ไม่ |

**เฟส 0 และ 1 คือ MVP** ปล่อยได้โดยไม่มีภาพสักใบและไม่แตะ `/my/*`

**ขอบเขตของแผน implementation ที่จะเขียนต่อจากสเปกนี้คือเฟส 0 และ 1 เท่านั้น**
เฟส 2 เป็นงานเนื้อหาที่เดินตาม `newplant_protocol.md` ไม่ใช่งานที่ต้องมีแผนโค้ด
ส่วนเฟส 3 และ 4 ต้องเขียนสเปกของตัวเองเมื่อถึงเวลา เพราะขึ้นกับผลของเฟส 1

### 7.1 เรื่องภาพ

ระบบต้องทำงานได้โดยยังไม่มีภาพ เพราะคุณค่าหลักของ `Landmark` อยู่ที่ `howToFind`
และ `confusedWith` ซึ่งเป็นข้อความ ภาพทำให้ดีขึ้นมากแต่ไม่ใช่เงื่อนไขที่ขาดไม่ได้

เครื่องมือปักหมุดในเฟส 3 ทำให้ภาพกลายเป็น **input ตอนใช้งาน ไม่ใช่ dependency ตอน build**
เพราะเครื่องมือเดียวกันรับทั้งภาพของเจ้าของระบบและภาพที่ผู้ใช้ถ่ายต้นตัวเอง

**ข้อจำกัดที่ระบุไว้ชัด** เฟส 3 คือ *ผู้ใช้ปักหมุดเอง ระบบตรวจสอบด้วยคำถามยืนยัน
แล้วคำนวณระยะตัดจาก `offsetMm` ให้* ไม่ใช่ระบบมองภาพแล้วหาข้อเจอเอง
การให้โมเดลหาตำแหน่งตัดอัตโนมัติเป็นงานที่ยังไม่มีหลักฐานว่าแม่นพอสำหรับการตัด
ที่ผิดแล้วต้นตาย และขัดกับกฎ "ห้ามแสดงตัวเลขที่ทำตามไม่ได้" ถ้าจะทำต้องอยู่ในสถานะ
"เดาให้ ผู้ใช้ยืนยัน" เสมอ และไม่อยู่ในขอบเขตรอบนี้

## 8 · การทดสอบ

คงแนวทางเดิมทั้งหมด คือ `renderToStaticMarkup` ไม่มี jsdom ไม่มี testing-library
component ที่แสดงผลเป็น sync ส่วน async อยู่ที่ `page.tsx` เท่านั้น
ตรรกะคำนวณเป็นฟังก์ชันบริสุทธิ์แยกจาก React

**กฎที่บังคับด้วยเทสต์ ห้ามแก้เทสต์เพื่อให้ผ่าน**

| กฎ | เหตุผล |
|---|---|
| ทุก `growthFormId` และ `genusId` ที่อ้าง ต้องมีอยู่จริง | แบบเดียวกับ `sourceIds` เดิม |
| `landmarkId` ใน `defaultExplant` และ `cutMarkers` ต้องมีในทรงนั้น | กันหมุดชี้ไปที่ไม่มีอยู่ |
| มี `point` ต้องมี `referenceImageId` | กันพิกัดลอยไม่มีภาพรองรับ |
| `botanical-fact` ที่ไม่มี `sourceIds` = fail | กันใช้ระดับนี้หนีการอ้างอิง |
| `Dose` ต้องมี `form`, `low`, `high`, `durationMin` ครบ | บังคับกฎเนื้อหาข้อ 1 ด้วยเครื่อง ไม่ใช่ด้วยตาอย่างเดียว |
| คำในทะเบียนที่โผล่ในเนื้อหาโดยไม่ถูกห่อ `<Term>` = fail | กันผู้เขียนคนต่อไปลืม |
| กฎจุดอ่อนที่สุดไม่นับ `botanical-fact` | ไม่งั้นกฎเสียความหมาย |
| ไฟล์สกุลต้องระบุว่าค่ามาจากชนิดใด ไม่ใช่แค่ว่ามาจากสกุลนี้ | กันการฟอกข้ออ้าง (ดู 9.2) |

**ข้อจำกัดที่ต้องยอมรับ** วิธีนี้จับพฤติกรรมข้ามหน้าและข้ามการโหลดใหม่ไม่ได้
`/find` เป็น flow หลายจอ จึงกำหนดว่า **เฟส 1 ต้องมี QA ผ่านเบราว์เซอร์จริง**
ไม่ใช่ smoke test ผ่าน curl อย่างเดียวเหมือนรอบที่แล้ว

## 9 · ความเสี่ยง

### 9.1 แปดทรงอาจแบ่งไม่ลงตัว

พืชบางชนิดคาบเกี่ยวสองทรง `/find` ต้องมีทางออก "ไม่แน่ใจ" ที่ไม่ใช่ทางตัน
และหน้าทรงต้องยอมรับได้ว่าผู้ใช้มาผิดทรง โดยมีทางกลับไปเลือกใหม่

### 9.2 ชั้นสกุลเป็นช่องให้ฟอกข้ออ้าง

การนำงานของชนิดหนึ่งไปวางไว้ที่ชั้นสกุลแล้วปล่อยให้ไหลลงไปหาทุกชนิดในสกุล
โดยติดป้าย "ประยุกต์" จะดูน่าเชื่อถือเกินความจริง จึงบังคับให้ไฟล์สกุลระบุว่า
ค่านั้นมาจากชนิดใด และให้ UI แสดงข้อมูลนั้นให้ผู้ใช้เห็น

### 9.3 งานเนื้อหาใหญ่กว่างานโค้ด

เฟส 2 คือการเขียน 8 ทรงและ 10 สกุลผ่านโปรโตคอลค้นหลักฐาน 9 ขั้นเต็ม
ซึ่งเป็นแรงหลักของโปรเจกต์นี้ ไม่ใช่การเขียนโค้ด

### 9.4 ของค้างเดิมที่ไม่แตะรอบนี้

- โซนหลังบ้าน (`LabShell`) ยังใช้ `globals.css` เดิมที่ทำไว้สำหรับโหมดสว่างอย่างเดียว
- การอัปโหลดรูปยังไม่เคยทดสอบกับ Firebase Auth และ Cloudinary จริง
- บันทึกต้นแม่เดิมยังเข้าถึงไม่ได้
- การล็อกเส้นทางอุปกรณ์กับรอบเพาะ

## 10 · สิ่งที่ตั้งใจไม่ทำ

- ไม่แตะ `/my/*` ทั้งหมด ยกเว้นจุดเชื่อมขั้นทดสอบช่วงในเฟส 4
- ไม่ทำ AI วิเคราะห์ภาพเพื่อหาตำแหน่งตัด
- ไม่ทำระบบชุมชนหรือการแชร์ผลรอบเพาะ
- ไม่แตะโครง dataset และ ML ที่มีอยู่ (`src/lib/domain/dataset-*`, `src/lib/image/*`)
- ไม่ย้ายฐานข้อมูล ไม่แก้ security rules

## 11 · ทางที่เปิดไว้แต่ยังไม่ทำ

- **นับคำค้นที่ไม่เจอ** เพื่อใช้เลือกลำดับการเขียนไฟล์สกุลด้วยข้อมูลจริงแทนการเดา
- **ระดับ `anecdotal` จากฟอรัมนักปลูก** ซึ่ง `newplant_protocol.md` อนุญาตอยู่แล้ว
  ใช้เติมสกุลที่ยังไม่มีงานวิจัยได้โดยไม่โกหกเรื่องระดับหลักฐาน
- **ผลรอบเพาะจากผู้ใช้จริง** เป็นแหล่งข้อมูลระยะยาวที่ไม่มีใครมี
