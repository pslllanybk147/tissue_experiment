# Manual-First Redesign — Design

## Problem

ระบบปัจจุบันแบ่งเมนูตามก้อนข้อมูล ไม่ได้แบ่งตามสิ่งที่ผู้ใช้ตั้งใจจะทำ ผลคือ

- คู่มือถูกขังหลัง workflow ต้องสร้าง Plant Record แล้ว Lot แล้วเลือก Protocol จึงจะอ่านเนื้อหาได้ ทั้งที่เนื้อหาอยู่ในโค้ดแล้วและอ่านได้ทันที
- มีตัวเดินขั้นตอน 4 ตัวทับซ้อนกัน คือ `protocol-runner`, `guided-protocol-runner`, `linear-protocol-runner-v2`, `beginner-step-guide` บวก `protocol-catch-up-panel`
- ศัพท์ระบบรั่วสู่ผู้ใช้ ได้แก่ Lot, Protocol, Template, Version, Evidence State, Claim Gate, Dataset intake, Model export
- ฟีเจอร์วิจัยและ ML กินพื้นที่เมนู 2 ใน 7 ช่อง ทั้งที่ไม่ใช่งานหลักของผู้ใช้
- เนื้อหาคู่มือมี 3 แหล่งที่ไหลออกจากกัน คือ `docs/philodendron/*.md` (18 ขั้น), `protocol-templates.ts` (standardSteps 13 ขั้น) และ monograph ที่สร้างขั้นจาก `tissueCulture.steps`
- `globals.css` ยาว 1,065 บรรทัดเป็น class เฉพาะกิจ ไม่มี component ร่วม ไม่มี elevation ทำให้ทุกหน้าแบนและหน้าตาเหมือนกันหมด

## Outcome

ผู้ใช้ที่ไม่เคยเข้าเว็บมาก่อนเปิดหน้าแรก เลือกต้นที่อยากทำ อ่านคู่มือครบทุกขั้นได้ทันทีโดยไม่ต้องล็อกอิน แล้วกดเริ่มรอบเพาะเมื่อพร้อมลงมือ ระบบบอกได้ว่าแต่ละขั้นมีงานวิจัยรองรับระดับไหน และคำนวณปริมาณสารให้ทำได้จริงด้วยอุปกรณ์ที่ผู้ใช้มี

## Scope Decisions

| หัวข้อ | สิ่งที่ตกลง |
|---|---|
| ขอบเขต rewrite | เก็บ `src/lib/domain` และ `src/lib/repositories` รื้อ `src/app` กับ `src/components` ใหม่ทั้งหมด — คำว่าเก็บหมายถึงไม่เขียนใหม่ทั้งชั้น แต่แก้เฉพาะจุดตามหัวข้อ Reuse and Rework ได้ |
| ผู้ใช้ | เปิดสาธารณะ อ่านคู่มือได้โดยไม่ล็อกอิน ล็อกอินเมื่อจะบันทึก |
| ฟีเจอร์ ML และวิจัย | ยกออกจากเมนูหลัก ย้ายไป `/admin` เก็บโค้ดและเทสต์ไว้ |
| แหล่งเนื้อหา | ไฟล์ในโค้ดเป็นต้นฉบับเดียว ผู้ใช้จดทับเฉพาะรอบของตัวเองใน Firestore |
| ภาพประกอบ | วาด SVG เป็น component ในโค้ด ครบทุกขั้น |
| ขอบเขตพืช | โครงต้องรองรับพืชนอก Philodendron |
| ภาษาดีไซน์ | Illustrated Step Book — เส้นขอบหนา เงาทึบไม่เบลอ สีสด ภาพประกอบทุกขั้น รองรับทั้งโหมดสว่างและมืด |
| ชื่อระบบ | Plantlover Lab |
| ระดับหลักฐาน | 3 ระดับ ตรงพันธุ์ / ประยุกต์ / ยังไม่มีงานรองรับ |
| การเพิ่มพืชใหม่ | ผู้ใช้ส่งเรื่องเข้ามา เจ้าของระบบอนุมัติก่อนเผยแพร่ |
| กระปุกเปล่าคุม | บังคับเฉพาะเส้นทางระดับ ยังไม่มีงานรองรับ นอกนั้นแนะนำ |

## Information Architecture

เหลือ 3 โซนจากเดิม 7 เมนู

| โซน | สิทธิ์ | เส้นทาง |
|---|---|---|
| คู่มือ | สาธารณะ | `/`, `/guide/<slug>`, `/guide/<slug>/step-<n>` |
| รอบเพาะของฉัน | ต้องล็อกอิน | `/my/rounds`, `/my/rounds/<id>`, `/my/rounds/<id>/step-<n>` |
| หลังบ้าน | เจ้าของระบบ | `/admin/manual/<slug>`, `/admin/submissions`, `/admin/dataset`, `/admin/research` |

`/admin/manual/<slug>` กางคู่มือที่ merge แล้วทั้งเล่มเพื่อตรวจทาน แก้ปัญหาที่อ่านไฟล์ pack แล้วเห็นแค่ส่วนต่าง

## Content Architecture — Core + Species Pack

แกนกลางเป็นคลังขั้นตอน ไม่ใช่ลำดับตายตัว แผ่นเสริมรายชนิดเป็นคนกำหนดลำดับ

```
manual/core/steps.ts        คลังขั้นตอนกลาง เขียนครั้งเดียว
manual/species/<slug>.ts    แผ่นเสริมรายชนิด
manual/registry.ts          รวม pack ทั้งหมด
```

แผ่นเสริมประกอบด้วย 4 ส่วน

- `sequence` เลือกและเรียงขั้นที่จะใช้ ถอดขั้นที่ไม่เกี่ยวออกได้
- `values` ทับค่าตัวเลขของขั้นที่มาจากแกนกลาง
- `overrides` ทับข้อความบางฟิลด์ เช่น เปลี่ยน `เลือกข้อ` เป็น `เลือกใบอ่อน`
- `steps` เขียนขั้นใหม่ที่แกนกลางไม่มี ใช้ schema เดียวกับขั้นปกติทุกฟิลด์

การ merge เกิดตอนโหลด ไม่ใช่ตอน build เพื่อให้ `/admin/manual/<slug>` แสดงผลลัพธ์เดียวกับที่ผู้ใช้เห็น

ตัวอย่างที่ตรวจแล้วว่ารองรับได้ Anthurium ที่ขยายผ่าน callus ใช้แกนกลางตรง 8 ขั้น ปรับค่า 3 ขั้น เขียนเอง 2 ขั้น ถอดออก 1 ขั้น รวมไฟล์เดียวโดยไม่แตะแกนกลาง

ข้อจำกัดที่ยอมรับ แกนกลางชุดนี้ใช้กับการเพาะเลี้ยงเนื้อเยื่อเท่านั้น การปักชำหรือตอนกิ่งต้องสร้างแกนใหม่ ไม่ออกแบบเผื่อในรอบนี้

## Equipment Capability Model

คู่มือระบุสิ่งที่ต้องได้ ไม่ระบุชื่ออุปกรณ์ กระบวนการต้องการ 4 อย่าง

| capability | ความหมาย |
|---|---|
| `sterile-medium` | อาหารปลอดเชื้อ |
| `sterile-water` | น้ำปลอดเชื้อสำหรับล้าง |
| `sterile-vessel` | ภาชนะและฝาปลอดเชื้อ |
| `surface-decontam` | ผิว explant สะอาด |

แต่ละ capability มีหลายวิธี แต่ละวิธีมี `evidenceLevel` และ `sourceIds` ของตัวเอง ผู้ใช้ติ๊กของที่มีในหน้า `ของที่ฉันมี` ระบบจับคู่ว่าทำวิธีไหนได้บ้างแล้วเลือกวิธีที่ระดับหลักฐานสูงสุด

**ระดับของเส้นทางรวมเท่ากับจุดที่อ่อนที่สุด ไม่ใช่จุดที่แข็งที่สุด**

การถามต้องถามเป็นของที่หาซื้อได้จริง ต้องมีตัวเลือก `หม้ออัดแรงดันทำอาหาร` แยกจาก `หม้อนึ่งความดันของแล็บ` เพราะที่ 15 psi ได้ 121 °C เท่ากันและเป็นของที่คนทำที่บ้านมี ถ้าถามด้วยคำว่า autoclave ผู้ใช้จะติ๊กว่าไม่มีทั้งที่มีของใช้แทนได้

เมื่อไม่มีวิธีใดทำ capability นั้นได้เลย ระบบต้องกางทางเลือกพร้อมความเสี่ยง ไม่ปล่อยผ่านเงียบ ๆ และไม่เลือกให้อัตโนมัติ

การต้มน้ำเดือด 100 °C ไม่นับเป็นน้ำปลอดเชื้อเพราะไม่ฆ่าสปอร์ ถ้าผู้ใช้ยืนยันจะใช้ ระบบติดป้าย ยังไม่มีงานรองรับ และบังคับกระปุกเปล่าคุม

## Evidence Model

ระดับหลักฐานผูกกับคู่ `พันธุ์ × วิธี` ไม่ผูกกับ profile ตายตัวอย่างที่ `sterilizationProfiles` ทำอยู่

| ระดับ | เงื่อนไข |
|---|---|
| ตรงพันธุ์ | มีงานที่ทำกับพันธุ์นี้ ด้วยวิธีนี้ ในบริบทนี้ |
| ประยุกต์ | มีงานรองรับวิธีนี้ แต่ทำกับพืชอื่นหรือบริบทอื่น |
| ยังไม่มีงานรองรับ | ไม่มีงานตีพิมพ์รองรับ บังคับกระปุกเปล่าคุมทุกรอบ |

ทุกระดับที่ไม่ใช่ ยังไม่มีงานรองรับ ต้องมี `sourceIds` อย่างน้อยหนึ่งรายการ ตรวจด้วยเทสต์

### ผลการตรวจหลักฐานเมื่อ 2026-08-02

- สูตรระยะตั้งต้น BAP 0.5 กับ NAA 0.05 mg/L ใน `philodendron-knowledge.ts` **หาที่มาไม่พบ** งานปี 2023 สรุปว่า BAP 1.0 mg/L เดี่ยวไม่ใส่ NAA ให้ยอดมากที่สุด ต้องแก้ตัวเลขหรือลดชั้น
- สูตรออกราก IBA 3.0 mg/L **ตรงกับงานปี 2023** คือ 3.2 ราก/explant และรากยาว 1.9 ซม.
- งาน Pink Princess ปี 2023 เริ่มจาก protocorm-like bodies และปี 2025 เพิ่มจำนวนใน temporary immersion จากยอดในขวด **ทั้งสองงานไม่มีขั้นฟอกผิวจากต้นแม่** ขั้น `surface-decontam` ของ Pink Princess จึงเป็น ยังไม่มีงานรองรับ และเส้นทางรวมตกชั้นตามไปด้วย
- เพิ่มแหล่งใหม่ งานฆ่าเชื้ออาหารด้วยสารเคมีสำหรับ Philodendron sp. `รวยทรัพย์` พบว่าเติมไฮเตอร์ 2 mL/L ลงในอาหารแทนการนึ่งยับยั้งจุลินทรีย์ได้ ให้ใบมากที่สุด 6.3 ใบ และต้นรอดทั้งหมดหลังออกปลูก 30 วัน เป็นสกุลเดียวกันและเริ่มจากยอดต้นจริง ใช้เป็นหลักฐานระดับประยุกต์ของ `sterile-medium` และ `sterile-vessel` เมื่อไม่มีหม้อนึ่ง

## Batch Calculator

ปัญหาของงานเล็กคือปริมาณเล็กจนชั่งไม่ได้และตวงไม่ได้ ไม่ใช่การคูณเลข

รับ input อย่างใดอย่างหนึ่ง

- จำนวนข้อหรือยอดที่ตัดมาได้ แล้วอนุมานจำนวนกระปุก
- จำนวนกระปุกที่ต้องการโดยตรง

ค่าที่เหลือระบบเติมให้และผู้ใช้แก้ได้ทุกช่อง ได้แก่ กระปุกเปล่าคุม 1 กระปุกสำรอง 1 ปริมาตรต่อกระปุก 25 mL และเผื่อสูญเสีย 15 เปอร์เซ็นต์ ค่าเผื่อของงานเล็กสูงกว่างานใหญ่เพราะสัดส่วนอาหารที่ติดค้างในภาชนะสูงกว่า

เมื่อคำนวณแล้ว ระบบเทียบทุกบรรทัดกับความละเอียดของเครื่องชั่งและอุปกรณ์ตวงที่ผู้ใช้ระบุไว้

- บรรทัดที่ชั่งไม่ได้ **ห้ามปัดเศษให้ดูเนียน** ต้องแสดงว่าชั่งไม่ได้แล้วพาไปทำน้ำยาแม่
- เมื่ออุปกรณ์ตวงหยาบเกินไป ระบบต้องย้อนคำนวณความเข้มข้นน้ำยาใช้งานใหม่ให้ตวงได้ พร้อมแสดงเปอร์เซ็นต์ความคลาดเคลื่อนก่อนและหลัง

ใช้โมดูลเดิมที่มีเทสต์แล้ว ได้แก่ `calculateMediumBatchPlan`, `calculateIntermediateStockDilution`, `calculateHaiterDose`

## Reuse and Rework

**ใช้ต่อได้เลย** `calculateMediumBatchPlan`, `calculateIntermediateStockDilution`, `calculateHaiterDose`, repository ทั้งหมด, `auth-session`, โครง Firestore ใต้ `users/{uid}`

**เขียนใหม่** ชั้น capability และตารางวิธี, ตัวจับคู่ของที่มีกับวิธีที่ใช้ได้, ตารางหลักฐาน `พันธุ์ × วิธี`, โหมด input จากจำนวนข้อ, การย้อนคำนวณความเข้มข้นจากความละเอียดอุปกรณ์, ระบบส่งเรื่องและอนุมัติพืชใหม่, `src/app` และ `src/components` ทั้งหมด, design token และ component ร่วมแทน `globals.css` เดิม

**แก้ของเดิม** `sterilizationProfiles` ย้าย `evidenceState` จาก profile ไปผูกกับคู่ พันธุ์ × วิธี และแตก profile เหมาเข่ง 2 ตัวเป็น capability ย่อยเพื่อให้ผสมข้ามกันได้, `philodendron-knowledge.ts` แก้สูตร BAP และ NAA ตามผลตรวจ

**ลบ** runner ทั้ง 4 ตัวและ `protocol-catch-up-panel` แทนที่ด้วยตัวเดียว

## Data Model Changes

- `EquipmentKit` เก็บใต้ `users/{uid}/settings/equipment` บันทึกว่าผู้ใช้มีอะไร ใช้ร่วมกันทุกรอบ
- `ResolvedPath` snapshot ของเส้นทางที่ระบบจัดให้ ล็อกไว้กับรอบเพาะตอนเริ่ม เพื่อให้ย้อนดูได้ว่ารอบนั้นใช้วิธีอะไรและระดับหลักฐานเท่าไร
- `RoundRecord` แทน `ExperimentLot` ในภาษาที่ผู้ใช้เห็น ชื่อ field ในฐานข้อมูลคงเดิมเพื่อไม่ต้อง migrate
- `PlantSubmission` เก็บพืชที่ผู้ใช้ส่งเข้ามา สถานะ pending / approved / rejected เจ้าของระบบอนุมัติผ่าน `/admin/submissions`

## Error Handling

- โหลดคู่มือไม่สำเร็จ แสดงเนื้อหาที่ bundle มากับหน้าได้เสมอเพราะเป็นไฟล์ในโค้ด ไม่ต้องรอเครือข่าย
- บันทึกรอบไม่สำเร็จ เก็บค่าที่กรอกไว้ในหน้าและแสดงปุ่มลองใหม่ ห้ามล้างสิ่งที่ผู้ใช้พิมพ์
- ผู้ใช้ยังไม่ได้ตั้งค่าอุปกรณ์แล้วเข้าขั้นที่ต้องใช้ ระบบพาไปหน้าตั้งค่าแล้วกลับมาที่ขั้นเดิม
- ค่าที่คำนวณแล้วออกนอกช่วงที่ปลอดภัย เช่น pH นอก 4 ถึง 7 ปิดปุ่มไปขั้นถัดไปพร้อมบอกเหตุผล

## Testing

- แกนกลางกับแผ่นเสริม merge แล้วได้ลำดับและค่าตามที่ pack กำหนด ครอบคลุมทั้งการทับค่า การแทรกขั้น และการถอดขั้น
- ทุกขั้นที่ระดับหลักฐานไม่ใช่ ยังไม่มีงานรองรับ ต้องมี `sourceIds` อย่างน้อยหนึ่งรายการ
- ระดับเส้นทางรวมเท่ากับจุดที่อ่อนที่สุดเสมอ ทดสอบด้วยชุด kit หลายแบบ
- เส้นทางระดับ ยังไม่มีงานรองรับ ต้องบังคับกระปุกเปล่าคุม
- เครื่องคำนวณ ตรวจว่าเมื่อค่าต่ำกว่าความละเอียดเครื่องชั่งต้องไม่ปัดเศษ และเมื่ออุปกรณ์ตวงหยาบต้องเสนอความเข้มข้นใหม่ที่ตวงได้
- คู่มืออ่านได้ครบทุกขั้นในสถานะไม่ล็อกอิน
- ตรวจ accessibility ด้วย `scripts/verify-accessible-ui.mjs` ที่มีอยู่แล้ว

## Build Order

งานนี้ใหญ่เกินหนึ่งแผน แบ่งเป็น 4 เฟส แต่ละเฟสมีแผนลงมือของตัวเอง

1. **Content core** แกนกลางกับแผ่นเสริม, registry, merge, ยุบขั้นเหลือ 14 และแก้ `docs/philodendron/*.md` ให้ตรง, แก้สูตรตามผลตรวจ, `/admin/manual/<slug>` — ไม่แตะ UI ผู้ใช้
2. **Public guide** design token สองโหมดสว่างและมืด, component ร่วม, หน้าแรก, หน้าคู่มือ, หน้าขั้นตอน, SVG ทั้งชุด, เปลี่ยนชื่อเป็น Plantlover Lab — อ่านอย่างเดียว ยังไม่มีการบันทึก
3. **Rounds** ล็อกอิน, ตัวเดินขั้นตอนตัวเดียว, การบันทึกค่าและรูป, ลบ runner เดิมทั้ง 4 ตัว — เขียนผ่าน repository interface เท่านั้นเพื่อเปิดทางให้เพิ่มออฟไลน์ภายหลัง
4. **Equipment and calculator** capability model, หน้าตั้งค่าอุปกรณ์, การจัดเส้นทาง, เครื่องคำนวณ, ระบบส่งเรื่องและอนุมัติ

## Resolved Items

- **โหมดมืด ทำ** ต้องออกแบบชุดสีมืดคู่กับชุดสว่างตั้งแต่เฟส 2 โดยยังคงภาษา Illustrated Step Book ไว้ คือเส้นขอบหนาและเงาทึบไม่เบลอ เงาในโหมดมืดใช้สีที่เข้มกว่าพื้นแทนสีดำล้วน และสีเน้นทั้งเหลือง เขียว ชมพู ต้องลดความสว่างลงให้ผ่านเกณฑ์คอนทราสต์บนพื้นเข้ม กำหนดเป็น design token ตั้งแต่ต้น ห้ามใส่ทีหลังด้วยการ invert
- **ชื่อระบบ Plantlover Lab** เปลี่ยนจาก Philodendron Lab ทุกที่ที่ปรากฏ ทั้ง brand ใน shell, `README.md`, `<title>` และ metadata
- **จำนวนขั้น 14 ยืนยันแล้ว** ยุบขั้นที่ซ้อนกันในเนื้อหาเดิม เช่นรวม review หลักฐานกับ export record เป็นปิดรอบและสรุปผล ต้องแก้ `docs/philodendron/*.md` ที่เขียนว่า 18 ขั้นให้ตรงกันด้วย

## Deferred Items

- **การจดตอนออฟไลน์ ยังไม่ทำในเฟส 3 คุยกันอีกครั้งหลังเฟส 3 จบ** ความเสี่ยงที่รับไว้คือถ้าภายหลังตัดสินใจว่าต้องมี ชั้นบันทึกของเฟส 3 อาจต้องรื้อ เพราะการเขียนตรงเข้า Firestore กับการเขียนผ่านคิวที่ซิงก์ทีหลังมีรูปร่างต่างกัน เพื่อลดความเสียหายให้เฟส 3 เขียนผ่าน repository interface เดิมเท่านั้น ห้ามเรียก Firestore SDK ตรงจาก component
