# Protocol Catch-up — Design

## Problem

ผู้ใช้มี Lot ที่เริ่มทำจริงไปแล้ว แต่ Protocol v2 บังคับบันทึกย้อนหลังทีละขั้น ทั้งเวลาและ note ทำให้ต้องทำงานเอกสารหลายรอบก่อนกลับไปทำขั้นปัจจุบัน ระบบจึงขัดกับเป้าหมาย beginner-friendly และทำให้ผู้ใช้ช้าลง

## Outcome

ผู้ใช้เลือกเพียงครั้งเดียวว่า `ตอนนี้จะเริ่มต่อจากขั้นไหน` ระบบปิดขั้นก่อนหน้าทั้งหมดให้พร้อมกันโดยไม่บังคับ note รูป หรือเวลารายขั้น แล้วเปิดขั้นที่เลือกทันที

## User Flow

1. บนหัว Protocol มีปุ่ม `ตั้งจุดเริ่มต่อ`
2. ระบบแสดงรายการขั้นทั้งหมดและให้เลือกขั้นแรกที่ผู้ใช้ยังไม่ได้ทำ
3. ระบบสรุปจำนวนขั้นที่จะปิดย้อนหลังและแสดงขั้น Timer ที่อยู่ในช่วงนั้น
4. สำหรับ Timer ที่ผ่านไปแล้ว ผู้ใช้กดยืนยันเพียงหนึ่งครั้งว่า `ครบเวลาที่กำหนดแล้ว`
5. วันที่โดยประมาณเป็นข้อมูลเสริม ไม่บังคับ และไม่มีช่อง note
6. ผู้ใช้กด `ยืนยันและเริ่มต่อจากขั้นนี้`
7. ระบบบันทึกขั้นก่อนหน้าทั้งหมดและเลื่อนไปยังขั้นที่เลือก

## Timer Rules

- Timer ที่ผู้ใช้ยืนยันว่าครบแล้วถูกข้ามได้ ไม่เริ่มเวลาใหม่
- Step Run ระบุว่าเป็นการยืนยันย้อนหลังโดยผู้ใช้และไม่สร้างเวลาเสร็จปลอมเมื่อผู้ใช้ไม่ได้ระบุวันที่
- หากผู้ใช้ไม่ยืนยัน Timer ระบบจะไม่ปิดขั้นนั้นหรือขั้นหลังจากนั้น และเปิด Timer ขั้นนั้นเป็นจุดเริ่มต่อ
- Timer ที่เริ่มแล้วแต่ยังไม่ครบยังใช้ตัวจับเวลาเดิมและนับเฉพาะเวลาที่เหลือ

## Data Model

- ขยาย `completionMode` ด้วย `carried-forward`
- เพิ่ม `carryForwardRecordedAt` และ `carryForwardTargetStepId`
- ขั้นที่ปิดย้อนหลังใช้ `status: Passed`, `note: ""`, ไม่มีรูป และเก็บ metadata ว่ามาจาก catch-up flow
- Audit History แสดง `ทำก่อนเริ่มใช้คู่มือ` ไม่แสดงเป็นการทำสด

## Persistence

- เพิ่ม `saveMany` ใน Step Run Repository
- Firestore ใช้ write batch เพื่อให้ Step Runs และ audit events สำเร็จหรือยกเลิกพร้อมกัน ป้องกันการปิดสำเร็จเพียงบางขั้น
- Memory repository บันทึกชุดข้อมูลแล้วเขียน demo storage ครั้งเดียว
- Lot และ Protocol version เดิมไม่ถูกแก้ไข

## Existing Single-step Retrospective Form

- ยังคงใช้ได้เมื่อผู้ใช้ต้องการแก้เพียงขั้นเดียว
- note เปลี่ยนเป็นไม่บังคับ
- ขั้นไม่มี Timer ไม่บังคับกรอกเวลาเริ่มและเวลาจบทั้งคู่; ใช้เวลายืนยันเป็น audit timestamp หากผู้ใช้ไม่ระบุ
- จุดหลักสำหรับ Lot ที่ทำมาแล้วคือ catch-up flow ไม่ใช่ฟอร์มรายขั้น

## Safety and Error Handling

- แสดงรายชื่อขั้นที่จะปิดก่อนยืนยัน
- ขั้น Timer ต้องได้รับการยืนยันชัดเจน
- เมื่อ batch write ล้มเหลว ไม่มีขั้นใดเปลี่ยนสถานะ และแสดงข้อความให้ลองใหม่
- ไม่ลบหรือเขียนทับ Step Run ที่ Passed อยู่แล้ว
- ขั้นที่มีผล `Needs review` หรือ `Failed` ต้องเตือนและไม่ถูกปิดทับโดยอัตโนมัติ

## Responsive UX

- Mobile ใช้ bottom sheet/section แนวตั้ง ปุ่มสูงอย่างน้อย 48px
- Desktop ใช้ dialog หรือ panel ในหน้าเดิม
- รายการสรุปต้องอ่านได้ที่ 360–1920px และไม่ใช้ตารางบีบข้อความ
- หลังยืนยัน เลื่อนไปหัวขั้นที่เลือกอัตโนมัติ

## Verification

- Unit tests: เลือกจุดเริ่มต่อ, Timer ยืนยัน/ไม่ยืนยัน, ไม่เขียนทับ Passed/Failed/Needs review
- Repository tests: atomic `saveMany`, metadata และ audit labels
- Browser test: สร้าง Pink Princess Lot เลือกเริ่มต่อจากขั้น 9 ปิดขั้น 1–8 ครั้งเดียว ยืนยัน Blank 48 ชั่วโมง และเปิดขั้น 9
- ตรวจ keyboard, reduced motion และ 14 viewport 360–1920px
- ผ่าน tests, lint, build, Firebase emulator และ sandbox ก่อน push `master`
