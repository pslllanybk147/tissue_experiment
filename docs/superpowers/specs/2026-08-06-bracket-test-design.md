# เฟส 4 · ขั้นทดสอบช่วง (bracket test)

> ลงวันที่ 6 สิงหาคม 2026 · สถานะ **อนุมัติแล้ว รอเขียนแผน implementation**
>
> ขยายจาก `2026-08-05-growth-form-first-redesign-design.md` ส่วนที่ 4.5 ซึ่งร่างแนวคิดไว้
> แต่ยังไม่ได้ออกแบบว่าเก็บข้อมูลอย่างไรและผลลัพธ์ไปไหนต่อ

## 1 · ปัญหาที่แก้

painpoint ข้อ 7 ที่บันทึกไว้ในสเปกหลัก **feedback loop ยาว** ทำผิดวันนี้ รู้ผลอีกสามสัปดาห์
จับคู่สาเหตุกับผลไม่ได้ มือใหม่จึงเรียนรู้ช้ามากแม้จะทำหลายรอบ

และปัญหาที่ตามมาจากเฟส 2 คือ **ทรงและสกุลจำนวนมากติดป้ายว่ายังไม่มีงานรองรับ**
เช่นทรงกล้วยไม้ทั้งทรง และขั้นฟอกของสกุล Anthurium ตอนนี้ระบบบอกได้แค่ว่าไม่มีตัวเลขให้
ซึ่งซื่อสัตย์แต่เป็นทางตัน

ขั้นทดสอบช่วงเปลี่ยนทางตันนั้นเป็นวิธีทำงาน คือ **ให้ต้นบอกค่าเอง** ด้วยการทดลอง
ที่ออกแบบไว้แล้ว แทนการลองผิดลองถูกแบบไม่มีโครง

---

## 2 · ของที่ต้องต่อก่อน

`Dose` ถูกสร้างไว้ตั้งแต่เฟส 0 ที่ `GrowthForm.defaultDoses` และ `GenusPack.doses`
แต่ **ยังไม่มีใครอ่านมันเลย** เพราะ `ManualStepDef` ไม่มีช่องรับ ค่าช่วงจึงไปไม่ถึงหน้าจอ

```ts
// ManualStepDef เพิ่มหนึ่งฟิลด์
doses?: Record<string, Dose>;
```

`resolve.ts` รวมค่าตาม cascade เดิม `form.defaultDoses → genus.doses → species`
โดยคีย์เดียวกันทับกันจากบนลงล่าง เหมือนที่ `overrides` ทำอยู่

**นี่คือส่วนที่ทำให้งานที่ค้างจากเฟส 0 มีความหมายขึ้นมาจริง** ถ้าไม่ต่อท่อนี้
ก็ไม่มีช่วงให้แบ่งเป็นสามชุด

## 3 · ผู้ใช้เจออะไร

### หน้าคู่มือสาธารณะ

ขั้นที่มี `doses` และระดับหลักฐานของขั้นนั้นไม่ใช่ `species-direct` จะขึ้นกล่อง

> **ยังไม่มีงานตรงพันธุ์ของต้นนี้ — อย่าเดา ให้ต้นบอกเอง**
> แบ่งชิ้นพืชเป็น 3 ชุด ชุดละ 3 กระปุก
> ชุด A ปลายต่ำ 0.8% · ชุด B กลาง 1.4% · ชุด C ปลายสูง 2%
> รู้ผลใน 14 วัน แล้วบันทึกลงรอบเพาะ

กล่องนี้เป็นข้อความอย่างเดียว **ไม่มีช่องกรอกและไม่มีข้อมูลเฉพาะบุคคล**
หน้าคู่มือจึงยังเป็น Server Component ที่ prerender ได้และอ่านโดยไม่ต้องล็อกอินตามเดิม

### ในรอบเพาะ

ขั้นเดียวกันใน `/my/rounds/<id>/step/<n>` มีตารางให้กรอก

| ชุด | ความเข้มข้น | ไม่ติดเชื้อ | ชิ้นยังเขียว | ใช้ได้จริง |
|---|---|---|---|---|
| A | 0.8% | ⬚ | ⬚ | ⬚ |
| B | 1.4% | ⬚ | ⬚ | ⬚ |
| C | 2.0% | ⬚ | ⬚ | ⬚ |

พร้อมช่องเดียวด้านบนว่า **กระปุกต่อชุด** เพราะทุกชุดใช้จำนวนเท่ากัน

**นิยามของแต่ละช่อง ต้องเขียนกำกับไว้ในหน้าจอ ไม่ใช่ให้ผู้ใช้เดา**

| ช่อง | นับกระปุกที่ |
|---|---|
| ไม่ติดเชื้อ | ไม่มีเมือก ไม่มีขนฟู วุ้นยังใส |
| ชิ้นยังเขียว | ชิ้นพืชไม่ดำและไม่เปื่อย ไม่ว่าจะติดเชื้อหรือไม่ |
| ใช้ได้จริง | **เข้าเงื่อนไขทั้งสองข้อพร้อมกัน** คือไม่ติดเชื้อและชิ้นยังเขียว |

สามช่องนี้ไม่ใช่ค่าที่คำนวณจากกันได้ เพราะกระปุกที่ติดเชื้ออาจยังเขียวอยู่
และกระปุกที่ไม่ติดเชื้ออาจชิ้นดำไปแล้ว จึงต้องนับแยกทั้งสามช่อง

**ทำไมต้องแยก "ไม่ติดเชื้อ" ออกจาก "ชิ้นยังเขียว"** เพราะสองอย่างนี้บอกทิศทางการแก้ที่ตรงข้ามกัน

| อาการเด่น | แปลว่า | ต้องทำ |
|---|---|---|
| ติดเชื้อเยอะ | ฟอกไม่พอ | เพิ่มความเข้มข้นหรือเวลา |
| ชิ้นดำเยอะ | ฟอกแรงเกิน | ลดลง และดูขั้นแก้ยางดำ |

ถ้าเก็บแค่ "ใช้ได้กี่กระปุก" ระบบจะบอกไม่ได้ว่าควรขยับไปทางไหนเมื่อทุกชุดล้มเหลว
ซึ่งเป็นกรณีที่มือใหม่ต้องการคำแนะนำมากที่สุด และเชื่อมกับคลังอาการที่มีอยู่แล้ว
(`browning-bleach-damage` กับ `contamination-fungal`/`contamination-bacterial`)

## 4 · การเก็บข้อมูล

**ไม่สร้าง collection ใหม่ ไม่แก้ security rules ไม่ migrate** ตรงกับหลักการใน
`project_summary.md` ส่วนที่ 5 ที่ว่ารอบเพาะแมปลงบนโครงข้อมูลเดิม

`ProtocolStepRun.measurements` เป็น `Record<string, number | null>` อยู่แล้ว ใช้คีย์แบบมีชื่อชุดต่อท้าย

```
bracket-jars-per-arm
bracket-a-dose   bracket-a-clean   bracket-a-alive   bracket-a-usable
bracket-b-dose   bracket-b-clean   bracket-b-alive   bracket-b-usable
bracket-c-dose   bracket-c-clean   bracket-c-alive   bracket-c-usable
```

`bracket-<arm>-dose` ระบบเป็นคนเขียน ไม่ใช่ผู้ใช้กรอก เพราะค่ามาจากการแบ่งช่วงของ `Dose`
เก็บไว้เพื่อให้ย้อนดูได้ว่ารอบนั้นทดสอบค่าอะไรจริง แม้คู่มือจะแก้ช่วงภายหลัง

**ความเสี่ยงของแนวทางนี้คือคีย์เป็นสตริงที่ตกลงกันเอง** พิมพ์ผิดแล้วเงียบ
เป็นความผิดพลาดแบบเดียวกับที่เพิ่งเจอในชั้นสกุลและในเมนูนำทาง จึงต้องมีฟังก์ชันสร้างคีย์
ที่เดียวและมีเทสต์คุม ห้ามพิมพ์คีย์ตรง ๆ กระจายตามไฟล์

## 5 · การตัดสินผลเป็นฟังก์ชันบริสุทธิ์

```ts
export type BracketArm = {
  armId: "a" | "b" | "c";
  dose: number;
  clean: number;
  alive: number;
  usable: number;
};

export type BracketOutcome =
  | { kind: "winner"; armId: "a" | "b" | "c"; dose: number; note: string }
  | { kind: "all-failed"; direction: "up" | "down" | "both"; note: string }
  | { kind: "incomplete"; note: string };
```

กฎการตัดสิน

1. ถ้ายังกรอกไม่ครบทุกชุด คืน `incomplete`
2. ถ้ามีชุดที่ `usable > 0` เลือกชุดที่ `usable` มากที่สุด
   **เสมอกันให้เลือกชุดที่ความเข้มข้นต่ำกว่า** เพราะเสียหายกับเนื้อเยื่อน้อยกว่าและใช้สารน้อยกว่า
3. ถ้าทุกชุด `usable === 0` ให้ดูว่าความล้มเหลวมาจากทางไหน
   - รวม `clean` น้อยกว่ารวม `alive` → `direction: "up"` ฟอกไม่พอ
   - รวม `alive` น้อยกว่ารวม `clean` → `direction: "down"` ฟอกแรงเกิน
   - เท่ากัน → `direction: "both"` พร้อมข้อความว่าเจอทั้งสองอย่าง ต้องแยกอาการก่อน

**เป็นฟังก์ชันบริสุทธิ์แยกจาก React** จึงทดสอบเคสเสมอกันและเคสล้มทุกชุดได้ครบ

## 6 · การจำค่าไว้ให้

เก็บที่ `users/{uid}/settings/calibration` ซึ่ง **security rules เดิมอนุญาตอยู่แล้ว**
(`match /users/{userId}/{document=**}` ให้เจ้าของอ่านเขียนได้) ใช้แพตเทิร์นเดียวกับ
`settings/equipment` ที่มีอยู่ คือ interface + ตัวจำในหน่วยความจำสำหรับโหมดสาธิต +
ตัว Firestore + factory ที่เลือกตามสถานะล็อกอิน

```ts
export type CalibrationEntry = {
  slug: string;
  stepId: string;
  doseKey: string;
  value: number;
  unit: string;
  jarsPerArm: number;
  usable: number;
  lotId: string;
  decidedAt: string;
};
```

คีย์ของ entry คือ `${slug}:${stepId}:${doseKey}` บันทึกทับได้เมื่อทดสอบรอบใหม่

### ข้อจำกัดที่ต่างจากที่เจ้าของระบบเลือกไว้

เจ้าของระบบเลือกว่า "จำไว้แล้วเอามาแสดงในคู่มือของคนนั้น" แต่**หน้าคู่มือสาธารณะ
เป็น Server Component ที่ prerender ตอน build และอ่านได้โดยไม่ต้องล็อกอิน**
การแสดงค่าเฉพาะบุคคลตรงนั้นจะพังทั้งสองอย่าง

**จึงแสดงที่สองที่แทน**

| ที่ | แสดงอะไร |
|---|---|
| `/my/rounds/<id>/step/<n>` | ค่าที่เคยทดสอบได้ของขั้นนี้ พร้อมวันที่และรอบที่มา |
| `/my` | รายการค่าที่ทดสอบได้ทั้งหมด |

ทั้งสองที่คือที่ที่ผู้ใช้อยู่ตอนลงมือจริงอยู่แล้ว ส่วนหน้าคู่มือสาธารณะแสดงแค่คำสั่งว่าต้องทดสอบ

ถ้าต้องการให้ขึ้นบนหน้าคู่มือสาธารณะจริง ต้องแลกด้วยการทำให้หน้านั้นเป็น client component
หรือเลิก prerender ซึ่งขัดกับกฎที่ตั้งไว้ตั้งแต่เฟส 1 จึงไม่ทำในเฟสนี้

## 7 · ความซื่อสัตย์เรื่องความน่าเชื่อถือ

**สามกระปุกต่อชุดไม่มีนัยสำคัญทางสถิติ** ทุกที่ที่แสดงค่าที่ได้จากการทดสอบ
ต้องกำกับข้อความว่า

> จากการทดสอบ 3 กระปุกต่อชุดในรอบเดียว ใช้เป็นจุดตั้งต้นที่ดีกว่าเดา ไม่ใช่ข้อพิสูจน์

และค่าที่จำไว้ **ห้ามยกระดับหลักฐานของขั้นนั้น** ขั้นที่เป็น `unsupported` ยังคงเป็น
`unsupported` ต่อไป เพราะการทดลองของผู้ใช้คนเดียวไม่ใช่งานที่ผ่านการทบทวน
ระบบแค่จำสิ่งที่ผู้ใช้พบ ไม่ได้เปลี่ยนสิ่งที่ระบบอ้าง

## 8 · การทดสอบ

คงแนวเดิม `renderToStaticMarkup` ไม่มี jsdom ตรรกะเป็นฟังก์ชันบริสุทธิ์แยกจาก React

| กฎที่บังคับด้วยเทสต์ | เหตุผล |
|---|---|
| คีย์ของบันทึกสร้างจากฟังก์ชันเดียว ห้ามพิมพ์ตรง ๆ | พิมพ์ผิดแล้วเงียบ แบบเดียวกับบั๊กชั้นสกุลและเมนูนำทาง |
| `chooseBracketWinner` เสมอกันต้องเลือกความเข้มข้นต่ำกว่า | ตรรกะที่ผิดแล้วดูไม่ออกด้วยตา |
| ทุกชุดล้มเหลว ต้องบอกทิศทางที่ถูก ทั้งขึ้น ลง และทั้งสองทาง | เป็นกรณีที่มือใหม่ต้องการคำแนะนำมากที่สุด |
| กรอกไม่ครบต้องคืน `incomplete` ไม่ใช่เดา | ห้ามสรุปจากข้อมูลที่ไม่ครบ |
| `doses` ต้องไหลผ่าน cascade ครบสี่ชั้น | ถ้าไม่ไหล ค่าช่วงจะไม่ถึงหน้าจอ |
| ค่าที่จำไว้ต้องไม่เปลี่ยนระดับหลักฐานของขั้น | กันการยกระดับหลักฐานด้วยข้อมูลของผู้ใช้คนเดียว |

**ต้องตรวจของจริงในเบราว์เซอร์** และครั้งนี้ต้องเข้าโหมดสาธิตหรือล็อกอิน
เพราะทุกอย่างที่เพิ่มอยู่หลังการล็อกอิน ต่างจากสามเฟสที่ผ่านมาที่ตรวจได้โดยไม่ต้องล็อกอิน

## 9 · ความเสี่ยง

**โหมดลงมือยังไม่เคยถูกเห็นของจริง** `.pl-do` ถูกเพิ่มในเฟส 1 แต่ QA รอบนั้นบันทึกไว้ว่า
ยังไม่ได้ตรวจเพราะต้องล็อกอิน เฟสนี้เป็นครั้งแรกที่จะได้เห็น อาจเจอปัญหาที่ค้างมาจากเฟส 1

**ตารางสามชุดบนจอ 360px** สี่คอลัมน์ในจอแคบอาจอ่านยาก ถ้าเจอจริงให้เปลี่ยนเป็นการ์ดต่อชุด
แทนตาราง แก้ที่การจัดวางไม่ใช่ที่ข้อมูล

**ผู้ใช้อาจกรอกตัวเลขที่ขัดกันเอง** เช่น `usable` มากกว่า `jars` หรือมากกว่า `clean`
ต้องเตือนตอนกรอก ไม่ใช่ปล่อยผ่านแล้วคำนวณผิด

## 10 · ตั้งใจไม่ทำในเฟสนี้

- **รวมผลข้ามผู้ใช้เพื่อปรับคู่มือกลาง** สเปกหลักระบุไว้ว่าไม่ทำระบบชุมชนในรอบนี้
  และมันมีปัญหาเรื่องคุณภาพข้อมูลกับความเป็นส่วนตัวที่ต้องออกแบบแยก
- **ทดสอบช่วงของขั้นอื่นนอกจากขั้นที่มี `Dose`** เช่นการทดสอบสูตรฮอร์โมนหลายสูตรพร้อมกัน
- **เตือนอัตโนมัติเมื่อครบ 14 วัน** ต้องมีระบบแจ้งเตือนซึ่งยังไม่มี
- **แก้ระดับหลักฐานจากผลการทดสอบ** ดูเหตุผลในส่วนที่ 7
